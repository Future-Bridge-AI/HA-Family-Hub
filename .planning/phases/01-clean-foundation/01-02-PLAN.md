## Phase Goal

**As a** developer, **I want to** work in a clean fork with one served copy of every file, **so that** each edit lands where Home Assistant loads it.

<objective>

Purpose: a developer edit can only land in the served copy (FOUND-01), and Italian, Dutch, Polish, Portuguese and Brazilian Portuguese users see Family Hub in their language (FOUND-02). Translations exist in exactly one place (FOUND-03).
Output: three commits, one per logical change (D-24): root JS deletions, language move, root translation deletions.

Decisions implemented: D-01, D-03, D-04 (root JS), D-05, D-06, D-07, D-08, D-09 (translations), D-24 (commit structure).
</objective>

## Scope note: file budget accepted, not split

`files_modified` lists 30 paths, more than the usual per-plan file budget. This is accepted on purpose rather than split, for these reasons:
- **No content edits.** Every path is a whole-file `git rm` or `git mv`. The executor never opens or edits these files; the gates read the JSON files only as data for key-parity checks. The 30 entries are 25 operations: the 5 language moves are each listed twice (source and destination).
- **Small context cost.** The estimate is about 45k tokens, inside one agent's budget. The file budget exists to cap editing context, and this plan does no editing.
- **Splitting would break locked commit structure.** D-24 (one logical change per commit) and D-04 (deletions in their own commits) make the 15-path removal one commit; the FOUND-01 concurrency truth depends on that. The FOUND-03 ordering truth requires the move commit to precede the deletion commit. Spreading these across plans would split one logical change, or add cross-plan ordering for no gain.
- **Each task is already one commit and one concern.** Task 1: 15 deletions. Task 2: 5 renames. Task 3: 5 deletions.
