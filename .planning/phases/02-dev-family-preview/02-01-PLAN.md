## Phase Goal

**As a** family product owner, **I want to** use a safe Family Preview of our week on my phone, **so that** I can try changes without risking Home.

<objective>
Slice 1 of the phase, for the developer: one command starts Dev. `scripts/dev-up` brings up a Dev Home Assistant on the pinned image, served over HTTPS from a local CA, with the working copy's integration mounted read-only, onboarded and named "Family Hub DEV" by the new seed tool. Edited card JS shows after `scripts/dev-cards` plus a normal refresh, and Python edits after `scripts/dev-restart`. The plan ends with the package-legitimacy checkpoint that gates every pip install later in this phase.

Purpose: DEV-01, DEV-02. It also lays down the shared pieces every later plan uses: the environment table (`tools/seed/envs.py`), the CA-pinned HA client, the per-environment credential store, the config-flow driver and the `LiveHA` test harness that runs a real HA 2026.10.4 in this sandbox.
Output: dev/ compose and config files, scripts (lib.sh, make-certs, dev-up, dev-cards, dev-restart, dev-down), the tools/seed package skeleton with bootstrap and resources-sync, live and unit tests.

Decisions implemented: D-01 (Dev own container, volume, port 8130), D-04 (host-agnostic tooling, one gitignored host env file), D-06 (HTTPS from day one, local CA), D-31 (core settings from the host env file). Discretion used: name-constrained openssl root CA instead of mkcert (D-06 allows either); the seed tool runs inside the pinned HA image on the laptop (`docker run ... python3 -m tools.seed`), so the laptop needs no Python installs and the tool uses exactly the aiohttp 3.14.5 and PyYAML 6.0.3 that HA 2026.10.4 ships; `configuration.yaml` has no `homeassistant:` core block, because any core key there switches HA's config source to YAML (homeassistant/core_config.py), so the seed owns `location_name` and the D-31 keys through `config/core/update`.
</objective>
