# Phase 2 — UI Design Contract

> Visual and interaction contract for Phase 2: Dev + Family Preview. Generated by gsd-ui-researcher (auto mode, no questions asked), verified by gsd-ui-checker.

**Scope of this contract.** Phase 2 is mostly infrastructure (Dev and Preview instances, seed, deploy/reset scripts). The UI surface is deliberately narrow, and it reuses the existing Family Hub card design system. Nothing here introduces a new design system, new fonts, new colours or a new component. The surfaces under contract are:

| # | Surface | Where it lives | Requirement |
|---|---------|----------------|-------------|
| S1 | Environment identity: server name, dashboard title, theme | HA core config, dashboard config, Family Hub settings (all written by the seed) | PREV-02, ACCESS-01 |
| S2 | Her dashboard and sidebar | Seed-created storage-mode dashboard; her per-user sidebar data | PREV-08, ACCESS-01 |
| S3 | Build stamp footer | `card/family-week-calendar-card.js` (served copy only) | PREV-07, ACCESS-05 |
| S4 | Loud delete confirmation (Dev and Preview only) | `card/family-week-calendar-card.js`, delete flow | D-09 |
| S5 | Seeded content she sees | Seed tool output (events, chores, rewards, meals, lists) | PREV-04, ACCESS-04 |
| S6 | "What changed, where to tap" hand-off note | `deploy-preview` terminal output for the developer | D-19 |
| S7 | Getting started guide | `docs/family/getting-started.md` plus `docs/family/img/` | ACCESS-03, ACCESS-04 |

Source of each decision is marked: **(D-nn)** = CONTEXT.md locked decision, **(R)** = 02-RESEARCH.md finding, **(code)** = read from the existing card code, **(default)** = auto-mode default recorded in Assumptions.

## Spacing Scale

Declared values (multiples of 4). Applies to anything NEW this phase adds to a `card/` file (the build stamp). Existing card CSS is not re-spaced.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Stamp top padding |
| sm | 8px | Stamp bottom padding |
| md | 16px | Stamp left padding (aligns with the card's own side margin) |
| lg | 24px | Gap between guide steps (Markdown, rendered by GitHub; informational) |
| xl | 32px | not used by new elements |
| 2xl | 48px | not used by new elements |
| 3xl | 64px | not used by new elements |

Exceptions:
- Stamp right padding is **96px** (a multiple of 4), reserved so the stamp never runs under the "+" add-event button (code: `.add-event-fab` is 56px wide, `right: 18px`, `position: fixed`; 56 + 18 + 22 gap = 96).
- Touch targets stay at the existing 44px minimum (`.modal-actions button { min-height: 44px }`). Phase 2 adds no new tappable element, so no new touch-target rule is introduced.

## Typography

Four sizes and two weights, all taken from values the cards already use (code: 12px and 13px are the most common sizes; 15px is the modal button size; 18px is the existing modal title size; 600 and 700 are the dominant weights). The only NEW text is the build stamp; the other rows document the roles the existing UI already plays so the executor does not invent values.

| Role | Size | Weight | Line Height | Used by in this phase |
|------|------|--------|-------------|-----------------------|
| Meta | 12px | 600 (environment word 700) | 1.4 | Build stamp (S3, new) |
| Body | 13px | 600 | 1.4 | Existing card body text; no new use |
| Label | 15px | 600 | 1.2 | Existing modal buttons; native-confirm buttons are OS-styled and out of our control |
| Heading | 18px | 700 | 1.2 | Existing modal titles; no new heading |

Why 12px and 13px both appear: both are existing card sizes that this phase does not change. 13px (Body) is documented only so the executor leaves existing body text alone; it is not used by any new element. The only new text, the build stamp, uses 12px (Meta) alone, so no new element sits one pixel from another size. No size is added or invented.

Display: not used in Phase 2 (no hero text). The guide (S7) is GitHub-rendered Markdown, so its type is GitHub's, not declared here.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#12141c` (`--fc-bg`) | Page and calendar background |
| Secondary (30%) | `#1a1d29` (`--fc-card`), `#232739` (`--fc-surface-alt`), `#1f2333` (surface2) | Cards, columns, modals, secondary buttons |
| Accent (10%) | `#c9a227` (`--fc-accent`), text on accent `#1a1400` | Existing uses only, see list below |
| Destructive | `#c0392b` border, `#a5281b` text, `#fdecea` fill | Existing fixed red of `.event-info-delete-btn` and `.fh-toast.is-error`. Not themed, unchanged |
| Text | `#e4e6f0` (`--fc-text`), secondary `#8b90a8` | Body; stamp uses `--fc-text` |

Accent reserved for (all existing, unchanged, no new accent use this phase):
1. Primary action buttons (`.btn-save`).
2. The "+" add-event floating button (`.add-event-fab`).
3. The today column outline and today's day number (`.day-col.today`, `.today .day-header .num`).

Environment colour identity, one distinct built-in theme per environment so the three never look alike:

| Environment | Theme id | Source |
|-------------|----------|--------|
| Preview | `midnight` (dark) | D-29 |
| Dev | `blossom` (pink, light) | (default) A1; distinct from both Preview and the default `slate` |
| Home | not decided here (do not use `midnight` or `blossom`) | D-17: "different from what Home will use" |

Contrast rule for the stamp: text colour is `--fc-text`, never `--fc-text-secondary`. Reason (calculated): `--fc-text-secondary` on `blossom` is about 3:1 against its card colour, below the 4.5:1 needed for 12px text; `--fc-text` clears it on both themes. The accent colour is not used for stamp text for the same reason (`blossom` accent is about 3:1).

## Surface Contracts

### S1. Environment identity (PREV-02, D-17, D-29)

No banner strip (D-17, D-deferred). Identity is carried by four cues that all say the same word:

| Cue | Preview | Dev |
|-----|---------|-----|
| HA location / server name (what the Companion app lists) | `Family Hub PREVIEW` (D-17) | `Family Hub DEV` |
| Dashboard title (shown in her sidebar and the dashboard header) | `Family Hub PREVIEW` (default, A2) | `Family Hub DEV` |
| Built-in theme | `midnight` | `blossom` |
| Build stamp (S3) | `Preview · <version>+<hash> · <time>` | `Dev · live` |

The words PREVIEW and DEV are upper case in names and titles so the name-match used by S4 is case-safe (`/\b(PREVIEW|DEV)\b/`, per R Pattern 6). The Home instance's name must never contain either word.

### S2. Her dashboard and sidebar (PREV-08, ACCESS-01, D-18)

One storage-mode dashboard, `url_path: family-hub`, `show_in_sidebar: true`, `require_admin: false`, icon `mdi:home-heart` (R). Every view is a **panel-type view holding exactly one card**, so each card gets the full screen.

| Order | View title | View `path` | View icon | Card | Card options |
|-------|-----------|-------------|-----------|------|--------------|
| 1 (opens first) | Calendar | `calendar` | `mdi:calendar-week` | `custom:family-week-calendar-card` | `people` from the seed's calendar mapping; `recipe_entity`, `meal_plan_entity`, `meal_templates_entity`, `suggestions_entity`, `reminders_entity` set to the five `todo.*` lists; `weather_entity` omitted (the card tolerates a missing weather entity, R Pitfall 16) |
| 2 | Today | `today` | `mdi:calendar-today` | `custom:family-today-card` | none |
| 3 | Chores | `chores` | `mdi:broom` | `custom:family-hub-chores-card` | `title: Chores` |
| 4 | Rewards | `rewards` | `mdi:star-circle` | `custom:family-hub-rewards-card` | `title: Rewards` |
| 5 | To-dos | `todos` | `mdi:format-list-checks` | `custom:family-hub-todo-card` | `title: To-dos`; `entities`: the seeded user-facing lists (see S5) |
| 6 | Recipes | `recipes` | `mdi:chef-hat` | `custom:family-hub-recipe-box-card` | `title: Recipes` |

Focal point (Calendar, the view that opens first): the **today column** of the week grid, drawn with the existing accent outline and accent day number (`.day-col.today`, `.today .day-header .num`; accent `#c9a227` on `midnight`). It is the one element that draws the eye first; the build stamp (12px, `--fc-text`, bottom row) and the "+" button are deliberately secondary. No new focal element is added.

Notes:
- Order follows D-18 (Calendar, Today, Chores, Rewards, To-dos, Recipes). The Pantry slot of D-18 is dropped while Grocy is off (A3).
- Every view has an icon so six tabs fit a phone header without text overflow. View titles remain set for accessibility and tooltips.
- Her profile is set so Calendar is what opens: `core.default_panel = family-hub` and the dashboard's first view is Calendar.
- Sidebar for her: only the Family Hub entry (plus the always-present profile and notifications). `hiddenPanels` is computed from her own `get_panels` per run, never hard-coded, and must include `theme-builder` (R Pattern 7).
- Cards keep their own existing "+" buttons; do not set `fab_position` (default `dashboard` stacking is fine with one card per view).

### S3. Build stamp footer (PREV-07, D-20, ACCESS-05)

A single line of small text, always visible on the Calendar view, so "did it update?" is never a guess.

Format (exact):

| Environment | Rendered text |
|-------------|---------------|
| Preview, after `deploy-preview` | `Preview · 2.0.0+a1b2c3d · 27 Oct 14:05` |
| Dev | `Dev · live` |
| Anything else (unsubstituted tokens and the HA name does not match DEV, for example Home) | **render nothing** (no element, no space) |

- Tokens in the card source: `__FH_BUILD_ENV__`, `__FH_BUILD_VERSION__`, `__FH_BUILD_TIME__`. `deploy-preview` substitutes them in the exported copy only (R Pattern 6). `__FH_BUILD_VERSION__` is `<manifest version>+<7-char git hash>`. `__FH_BUILD_TIME__` is pre-formatted by the script as `D Mon HH:mm` (24-hour, host time zone, no leading zero on the day, English month abbreviation) so the card does no date maths.
- Separator is a middle dot with a single space either side (` · `, U+00B7).
- The environment word ("Preview" or "Dev") is weight 700; the rest is weight 600. No colour change between the parts.
- One additional `console.info` line carries the same text (D-20). No other logging.
- The text is hard-coded English, not run through `_t()`, and adds no keys to `translations/*.json` (A4: avoids breaking the 2,139-key parity that Phase 3 CI-04 will guard).

Placement and style:
- **Position:** a non-scrolling row at the bottom of the card, below the calendar grid, inside the card's own root (not inside any modal or overlay; the add-event modal sits directly before `</ha-card>` and must not contain it). The card host is `height: 100dvh; overflow: hidden` with an internally scrolling grid (code), so the stamp must be a `flex: 0 0 auto` row outside the scroll area or it will be pushed off screen. The executor must verify it is visible without scrolling on a 360 x 800 phone viewport and a 1280 x 800 desktop viewport.
- **Alignment:** left aligned (so it clears the "+" button on the right). Padding: `4px 96px 8px 16px`.
- **Type:** 12px, line-height 1.4, `color: var(--fc-text)`, `overflow-wrap: anywhere`, wraps to a second line rather than truncating. `user-select: text` so she can copy it into a message.
- **Not interactive:** no hover, no tooltip, no click handler. `aria-label` is not needed (it is plain text), but it is a normal text node so screen readers read it.

### S4. Loud delete confirmation (D-09)

Mechanism (recommended, R Pattern 6): reuse the location name. The extra prompt appears only when **all** are true:
1. `this._hass.config.location_name` matches `/\b(PREVIEW|DEV)\b/`.
2. The `family_hub/calendar/delete_support` answer for that calendar has `platform === "google"`. The card's `_getCalendarDeleteSupport` must pass the existing `platform` field through (today it drops it; one added property).
3. The event summary does **not** start with the exact seed tag `[PREVIEW] ` or `[DEV] ` (those are pretend events; see A5).

Flow, hooked into the existing `window.confirm` in `_wireEventInfoDeleteButton` (code, ~line 23685):
1. The existing standard confirm shows first, **unchanged**.
2. If it is accepted and the three conditions hold, a **second** `window.confirm` shows with the loud copy below.
3. Cancel at either prompt aborts silently (no toast, no change; the button stays as it was). Nothing else in the flow changes. Delete failure still uses the existing alert.

The prompt is a native browser/WebView confirm, like the existing one: it cannot be restyled and its OK/Cancel buttons are OS-styled. Do not build a custom modal (keeps the change small and inside the D-09 brief). Truncate `summary` to 80 characters plus `…` so the dialog stays readable.

Copy (exact; `{env}` is `Preview` or `Dev`; `{person}` is the calendar's person name; `{summary}` truncated as above):

```
THIS IS THE REAL FAMILY CALENDAR.

You are in {env}, but "{summary}" is on {person}'s real Google Calendar. Deleting it here deletes it for the whole family, and Family Hub cannot undo it.

Delete it anyway?
```

Not shown on Home, on Local Calendars, or for tagged seed events. Add and edit flows are **not** guarded by D-09; see Assumption A6 and the open item in the return summary.

### S5. Seeded content she sees (PREV-04, D-12, D-14)

All text is invented, family-friendly and plain. The repo ships only the invented example family; real first names come from the gitignored local file (D-12). Content is date-relative to today.

Invented example family (`tools/seed/data/family.example.yaml`): **Sam** (parent, admin-capable, stand-in for the developer), **Jordan** (parent, non-admin, stand-in for her), **Riley** (child, age 9), **Casey** (child, age 6).

Volume and shape rules the seed must satisfy (these make "find today's plan, tick a chore, redeem a reward" work on any day):

| Area | Rule |
|------|------|
| Calendar events | Current week and next week, week-anchored (R Pattern 5.6). 1 to 3 events per day on most days; **one day with no events**, **one day with 4 events** (exercises overflow), **one all-day event**, **one event shared by two members**. On today: at least one all-day or morning event and at least one event at 16:00 or later, so something is still upcoming for most of the day |
| Event titles | Prefix `[PREVIEW] ` (Dev `[DEV] `), exact, one trailing space. Examples: `[PREVIEW] School drop-off`, `[PREVIEW] Dentist`, `[PREVIEW] Football practice`, `[PREVIEW] Piano lesson`, `[PREVIEW] Family movie night`, `[PREVIEW] Grandma visits` |
| Meals | Dinner on 5 or 6 of the next 7 nights (D-14: most nights), one night blank on purpose. Examples: Spaghetti night, Tacos, Pancakes for dinner, Roast chicken, Pizza Friday, Soup and bread |
| Chores | 4 to 6 per child; **at least 2 per child due today**; a mix of daily and weekly; none overdue at seed time. Examples: Make your bed, Feed the cat, Set the table, Take out the recycling, Tidy toys, Read for 15 minutes. She can complete one with no extra PIN step (verified as a non-admin, R 2026-10-28) |
| Rewards | 5 rewards. Start each child with a star balance so the **cheapest reward is affordable and the most expensive is not**, showing both the redeemable and the "not enough stars" states. Examples: Choose the movie (15 stars), Extra screen time, 30 minutes (10), Stay up 30 minutes late (20), Ice cream trip (25), Pick a small toy (40) |
| Goal and routine | One goal per D-14 (example: Tidy room 5 days in a row, target 5) and one morning routine (Brush teeth, Get dressed, Pack school bag) |
| To-do lists for her To-dos view | In addition to the five required system lists, two plain lists: **Groceries** (6 items) and **Errands** (3 items). These two feed the To-dos card `entities` |
| Recipes | 3 (Spaghetti bolognese, Veggie tacos, Banana pancakes), each with ingredients and 3 to 5 steps |
| Accounts | Names as in the family file. Login usernames lower-case first name; passwords generated, never in the guide or repo (R Pattern 3 step 6) |

Event `description` carries the machine marker `family-hub-seed:<env>:<key>` (R Pattern 5.6). It is visible if someone opens an event's notes; that is accepted and not styled.

### S6. "What changed, where to tap" hand-off note (D-19)

Printed by `deploy-preview` on success, for the developer to pass on in person or by text. Plain language, no commit hashes in the sentences meant for her. Lines are at most 72 characters so it reads in a terminal and pastes cleanly into a text message.

Exact shape (`<...>` are filled in; the two description lines come from a `--note` style input or prompt chosen by the planner; if none is given print the fallback line):

```
Preview is updated and ready for you to try.

What changed:  <one plain sentence in her words, no jargon>
Where to look: Open Family Hub PREVIEW, tap <View name>, then <what to tap>.
Check it is new: the small line at the bottom of the Calendar should say
                 "Preview · <version>+<hash> · <time>".
```

Fallback when no note is supplied: `What changed:  (no note was given - tell her what changed yourself)`. The deploy still succeeds.

On failure `deploy-preview` prints a developer-facing error (not for her) and **does not** print the "ready for you" line.
